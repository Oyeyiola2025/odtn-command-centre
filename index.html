            About this project

            About & security design

            The scenario

            Based on the Operation Defend the North (ODTN) Ontario kickoff scenario: a hypothetical supply-chain cyberattack shortly before Christmas causing widespread payment-processing failures across retail, pharmacies, transportation and government. The exercise’s five modules – technical evidence, system logs, customer complaints, conflicting information and internal communication – map directly to this site’s decision simulator.

            Lessons are also drawn from other ODTN sessions reviewed: the Vancouver lessons-learned session (human factors, crown jewels), the Ottawa proactive-defence module (containment, incident command, vendor security) and the Calgary recovery simulation (staged recovery, client priorities).

            Audience & purpose

            Students, junior SOC analysts and non-technical managers who need to understand what a cross-sector cyber incident feels like from the inside – and practise the decisions it demands – in a safe setting.

            Built with

            Plain HTML, CSS and JavaScript with no frameworks, libraries or third-party scripts. Built with AI assistance (Claude), with every file reviewed against the security checklist on the right.

            Security by design

            • No secrets. No API keys, tokens or credentials exist anywhere in the code – there is nothing to leak.
            • No backend, no data collection. Nothing you type leaves your browser. No forms submit to a server, no analytics, no cookies.
            • Strict Content-Security-Policy. Only this site’s own scripts and styles may run; no inline scripts, no eval, no external connections, and the site cannot be framed (clickjacking).
            • No innerHTML. All dynamic content is built with textContent and DOM APIs, so input can never become executable HTML (XSS).
            • Allow-list input validation. The name field accepts only letters and a few punctuation marks, length-limited; log search is length-limited and uses plain text matching (no user-supplied regex).
            • Untrusted storage. Progress saved in sessionStorage is re-validated on load, so tampered values are discarded rather than trusted.
            • Hardened headers. HSTS, nosniff, no-referrer, frame denial and a locked-down Permissions-Policy.
            • Safe indicators. All IPs and domains use reserved documentation ranges (RFC 5737, .example) so nothing points at a real system.
            • No fake login. Role selection is deliberately not “authentication” – adding passwords to a site with nothing to protect would only create attack surface.

            Known limitations

            Scores are calculated in the browser, so a determined user can alter their own score with developer tools. That is acceptable for a no-stakes training tool; any graded or competitive version would need server-side scoring.
